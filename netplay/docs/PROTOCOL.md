# ac6net wire protocol v1

This document is normative for both the C++ client (`netplay/core`) and the Go server
(`netplay/server`).

- **Byte order:** little-endian (LE) unless a field says BE.
- **Datagrams:** every datagram is one UDP payload starting with the magic byte `0xA6`.
- **Size:** a datagram, including relay framing, never exceeds 1400 bytes.

## 1. Cryptography

| Item | Definition |
|---|---|
| Keypairs | X25519. The secret key is 32 random bytes; `pk = X25519(sk, basepoint)`. Monocypher `crypto_x25519_public_key`; Go `ecdh.X25519()`. |
| DH | `dh = X25519(my_sk, their_pk)` (32 bytes). Monocypher `crypto_x25519`. |
| KDF | `KDF(dh, label, parts…) = BLAKE2b-256(key = dh, message = label ‖ parts…)`. Keyed BLAKE2b with a 32-byte key and a 32-byte digest. Monocypher `crypto_blake2b_keyed`; Go `blake2b.New256(dh)`. `label` is the ASCII bytes with no terminator. |
| AEAD | XChaCha20-Poly1305 (IETF/libsodium construction) with a 24-byte nonce and a 16-byte tag appended after the ciphertext. Monocypher `crypto_aead_lock`/`unlock` (XChaCha20 + Poly1305, RFC 8439 padding); Go `chacha20poly1305.NewX`. |
| Nonce | `ctr` (u64 LE, 8 bytes) followed by 16 zero bytes. `ctr` starts at 1 and increases by 1 per packet sent with that key. |
| Replay | The receiver keeps the highest `ctr` seen per key plus a 1024-bit window, and drops duplicates or anything older than the window. |
| Boot ID | 8 random bytes generated at process start. Every key mixes in the boot IDs of both ends, so a restart never reuses a (key, nonce) pair. |

The compatibility test vectors are in `netplay/core/tests/vectors.json`, generated by
`go run ./cmd/vectors`. Both implementations must pass them.

## 2. Packet types

```
type  dir    name
0x01  C→S    HELLO
0x02  S→C    HELLO_ACK
0x03  C→S    C2S        (encrypted control after HELLO)
0x04  S→C    S2C        (encrypted control)
0x05  S→C    REHELLO    (clear; server lost the client's state; client must send HELLO again)
0x06  C→S    RELAY      (forward an inner P2P packet to another peer)
0x07  S→C    RELAYED
0x10  P↔P    P2P        (peer packet; sent directly or carried inside RELAY/RELAYED)
```

### 2.1 HELLO (0x01), client → server

```
off  size  field
0    1     0xA6
1    1     0x01
2    32    c_pk         client static public key
34   8     c_boot       client boot id
42   8     ctr          u64 LE
50   n+16  AEAD(c2s_key, nonce(ctr), ad = bytes[0..50), plaintext = JSON hello)
```

The keys:

- `c2s_key = KDF(dh(c_sk, s_pk), "AC6NET-C2S-1", c_pk, s_pk, c_boot)`.
- The server derives the same key from `dh(s_sk, c_pk)`.

The JSON hello is:

```json
{"v":1,"client":"ac6recomp-netplay/0.1","gamertag":"Talisman","title":"4E4D07D1",
 "compat":"<hex32>","local":[["192.168.1.20",51234],["2001:db8::5",51234]],"privacy":false}
```

`local` lists this socket's local candidate addresses: non-loopback IPv4 plus global IPv6, all at
the client's UDP port. With `lan = false` it is empty. Loopback (127.0.0.1) is added only when
the client is talking to a loopback server (dev and test).

### 2.2 HELLO_ACK (0x02), server → client

```
0    1     0xA6
1    1     0x02
2    8     s_boot
10   8     ctr
18   n+16  AEAD(s2c_key, nonce(ctr), ad = bytes[0..18), JSON)
```

The key is `s2c_key = KDF(dh, "AC6NET-S2C-1", c_pk, s_pk, c_boot, s_boot)`.

```json
{"v":1,"peer_id":"9f3c...16hex","xuid":"0009...16hex","vip":"10.64.0.7","gamertag":"Talisman",
 "public":["203.0.113.9",40123],"server_time_ms":1760000000000,"motd":""}
```

- `peer_id`, `xuid` and `vip` are stable per `c_pk`, and persisted by the server.
- `public` is the server-observed source address of the HELLO (the reflexive address).
- The server answers a repeated HELLO with the same `c_boot` idempotently; the `ctr` keeps
  increasing.
- A new `c_boot` for a known `c_pk` replaces the old registration (the client restarted). The
  server drops the old boot's sessions only after the 30 s liveness timeout, or immediately
  if the old boot has no sessions.

### 2.3 C2S (0x03), client → server

```
0    1     0xA6
1    1     0x03
2    8     peer_id      u64 LE (the server-assigned id)
10   8     c_boot
18   8     ctr
26   n+16  AEAD(c2s_key, nonce(ctr), ad = bytes[0..26), inner)
```

If the server does not know `(peer_id, c_boot)`, it replies REHELLO.

The inner message is `kind (u8)` followed by its body:

| kind | name | body |
|---|---|---|
| 0x10 | RPC_REQ | `req_id u32, frag_idx u8, frag_cnt u8, bytes` (fragment of the JSON request; ≤1100 bytes per fragment; at most 32 fragments) |
| 0x11 | KEEPALIVE | `JSON {"local":[...]}` (optional; may be empty, 0 bytes) |
| 0x12 | INTRO_REQ | `req_id u32, by u8 (1 = vip, 2 = peer_id), value (u32 vip in network order for by=1, u64 LE peer_id for by=2)` |
| 0x13 | BYE | empty; the client is shutting down |

### 2.4 S2C (0x04), server → client

```
0    1     0xA6
1    1     0x04
2    8     s_boot
10   8     ctr
18   n+16  AEAD(s2c_key, nonce(ctr), ad = bytes[0..18), inner)
```

| kind | name | body |
|---|---|---|
| 0x20 | RPC_RESP | `req_id u32, frag_idx u8, frag_cnt u8, bytes` (fragment of the JSON response) |
| 0x21 | KEEPALIVE_ACK | `JSON {"public":["ip",port]}` |
| 0x22 | INTRO | `req_id u32` (0 if unsolicited) + `JSON peer record` (below) |
| 0x23 | INTRO_FAIL | `req_id u32, reason u8 (1 = unknown, 2 = offline, 3 = refused)` |
| 0x24 | NOTICE | `JSON {"code":"...","msg":"..."}` (for example a kick or a shutdown notice) |

The peer record in an INTRO:

```json
{"peer_id":"16hex","vip":"10.64.0.9","pk":"64hex","boot":"16hex","xuid":"16hex","gamertag":"Bird",
 "cands":[["192.168.1.30",50555,"lan"],["203.0.113.40",61000,"srflx"],["2001:db8::9",50555,"v6"]]}
```

**Candidate rules** (server-side):

- Peers that share a public IPv4 get each other's `lan` candidates.
- Peers on different public IPs get `srflx` (the server-observed address) plus `v6`.
- A peer with `privacy: true` gets an empty `cands` list in records sent about it.
- Loopback candidates are included only when both peers registered from loopback.

**When the server introduces:** when A sends INTRO_REQ for B and both are online, the server:

1. records the pair (A, B) as introduced (this authorizes relaying between them);
2. sends INTRO(B) to A with A's `req_id`;
3. sends INTRO(A) to B with `req_id = 0`.

Each INTRO is resent at most 3 times, every 500 ms, until the receiving side sends any packet to
the server with a later `ctr`. In practice, B's KEEPALIVE or RPC confirms it.

### 2.5 REHELLO (0x05), server → client, clear

```
0  1  0xA6
1  1  0x05
```

The client re-sends HELLO, rate-limited to 1 per second.

### 2.6 RELAY (0x06) and RELAYED (0x07)

```
RELAY:   0xA6 0x06  src_peer_id u64  dst_peer_id u64  inner P2P packet (starts with 0xA6 0x10 …)
RELAYED: 0xA6 0x07  src_peer_id u64  inner P2P packet
```

The server forwards RELAY as RELAYED only if all of these hold:

- the datagram's source address equals the registered address of `src`;
- `dst` is online;
- (src, dst) was introduced;
- per-source rate limits allow it: 2000 packets/s and 4 Mbit/s averaged over 1 s.

Otherwise the packet is dropped silently. The inner packet is end-to-end encrypted; the server
never decrypts it.

### 2.7 P2P (0x10), peer ↔ peer

```
0    1     0xA6
1    1     0x10
2    8     src_peer_id  u64 LE
10   8     ctr
18   n+16  AEAD(send_key, nonce(ctr), ad = bytes[0..18), inner)
```

The keys:

- `send_key(S→R) = KDF(dh(S_sk, R_pk), "AC6NET-P2P-1", S_pk, R_pk, S_boot, R_boot)`.
- The receiver derives the same key with `dh(R_sk, S_pk)`, and uses the opposite order to build
  its own send key.

A packet from a `src_peer_id` with no INTRO record yet is buffered: at most 8 packets per source
and 64 in total, for up to 2 s. The receiver then sends INTRO_REQ(by peer_id). The buffered
packets are decrypted once the INTRO arrives.

The inner message is `kind (u8)` followed by its body:

| kind | name | body |
|---|---|---|
| 0x01 | PROBE | `probe_id u64, t_us u64` (sender clock) |
| 0x02 | PROBE_ACK | `probe_id u64, t_us u64` (echo) |
| 0x03 | KEEPALIVE | empty |
| 0x04 | DATA | `channel u8`, then the payload (see below) |
| 0x05 | BYE | empty; the peer is going away (drop streams now) |

**Path rules:**

- A PROBE may arrive on any address. The receiver answers PROBE_ACK to the PROBE's source address,
  over the same transport it arrived on (direct, or via RELAYED → RELAY).
- A PROBE_ACK that arrives directly from address X validates direct path X, with RTT = now −
  t_us.
- A peer sends DATA on its current best path: a validated direct path if any, else the relay.
- On receiving any authenticated packet directly from X, the receiver may adopt X as a
  peer-reflexive candidate and probe it.

### 2.8 DATA channels

`DATA = 0x04, channel u8, payload`. The payload format belongs to the subsystem that owns the
channel:

| channel | owner | payload |
|---|---|---|
| 0x01 | vnet datagram | `proto u8 (17 = udp, 254 = vdp), src_port u16 BE, dst_port u16 BE, msg_id u16, frag_idx u8, frag_cnt u8, bytes` |
| 0x02 | vnet stream (KCP) | raw KCP segment(s), conv = connection id |
| 0x03 | vnet stream control | `type u8 (1 SYN, 2 SYNACK, 3 RST, 4 FIN, 5 FINACK), conn_id u32 LE, src_port u16 BE, dst_port u16 BE` |
| 0x04 | qos | `type u8 (1 REQ, 2 RESP), xnkid 8 bytes (guest order), seq u32, t_us u64, [RESP only: status u8 (0 ok, 1 not listening), data_len u16, data]` |

Connection IDs: `conn_id = (initiator_is_lower_vip ? 0x80000000 : 0) | counter`. `counter` is
a 31-bit value, unique per initiating process.

## 3. RPC

- **Request:** `{"id":<req_id>,"m":"<method>","a":{...}}`. **Response:**
  `{"id":<req_id>,"ok":true,"r":{...}}` or `{"id":..,"ok":false,"err":"code","msg":"text"}`.
- **Fragmentation:** a request or response longer than 1100 bytes is split into fragments. The
  receiver reassembles by (`req_id`, `frag_cnt`).
- **Retransmission:** the client resends every fragment of an unanswered request every 300 ms,
  until a response or the per-call timeout (default 6 s; search 8 s).
- **Duplicates:** the server caches each client's last 64 responses by `req_id` for 60 s, and
  answers a duplicate request from the cache without re-executing it.
- **ID encoding:** XNKID, XUID and peer_id are 16 lower-case hex digits; XNKEY is 32 hex. vIPs are
  dotted quads. Binary values are standard base64 with padding.

**Error codes:**

| code | meaning |
|---|---|
| `bad_request` | malformed request |
| `not_found` | no such session, account or row |
| `not_host` | the call needs the session host |
| `full` | the session has no open slots |
| `state` | the session is in the wrong state for this call |
| `compat` | the compat key does not match |
| `rate` | rate limit hit |
| `internal` | server error |

**XUSER data:**

- A **context** is `[id, value]`, with `id` and `value` as u32.
- A **property** is `{"id":u32,"t":type,"v":value}`. The type is XUSER_DATA_TYPE: 1 int32,
  2 int64, 3 double, 4 unicode (`v` = base64 of the guest UTF-16BE bytes, including the
  terminator), 5 float, 6 binary (base64), 7 datetime (int64), 0 context. Numbers are JSON
  numbers. int64 must round-trip exactly, so the Go server decodes with `UseNumber`.

### 3.2 Server rules

- **Session IDs:** `0x80` in the top byte plus 56 random bits. XNKEY is 16 random bytes; the
  nonce is a random u64.
- **Host:** the account that called `session.create`.
- **Membership:**
  - A host's `session.join` may add any XUIDs; the server treats that as the host admitting
    remote players.
  - A non-host may join or leave only its own XUID.
  - `filled_*` counts the distinct members. The host is counted only once its XUID joins (AC6
    joins the host's local user explicitly).
- **Search filters:**
  - title and compat match;
  - `flags & 0x8` (matchmaking) is set;
  - state is lobby, or `flags & 0x400` is clear;
  - `public_slots − filled_public ≥ num_users`;
  - every search context's ID exists in the session with an equal value.

  v1 ignores properties when filtering. Results are newest first, at most `max_results`; the
  searcher's own sessions are excluded.
- **Liveness:**
  - A client is offline after 30 s without any authenticated packet.
  - When a host goes offline, its sessions are deleted.
  - When a member goes offline, it is removed from sessions.
  - A session with no update for 2 h is deleted.
- **Arbitration:** `session.arbitrate` records the caller with its machine ID
  (`0xFA00000000000000 | 48-bit MAC`, MAC = `00 22 48` + low 24 bits of the vIP). It returns
  every current member grouped by machine, in join order, trust 1.
- **Stats:** a write replaces each column value (aggregation "last"). Ranks are by the first
  column descending. Phase 2 uses the SPA aggregation types.
